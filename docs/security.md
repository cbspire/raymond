# Security and privilege boundaries

Raymond serves local HTTP only. Loopback is not an authentication boundary: any local process can reach the proxy. All targets are IPv4 loopback literals; domains and ports are validated. Backend connections are the only application runtime network traffic. DNS never forwards. Forged Forwarded/X-Forwarded headers are discarded; known client address, original Host and HTTP scheme are inserted. HTTPS, caching and rewriting are excluded.

Installation is a separate administrator action. Resources are exclusively created from fixed templates and a validated YAML schema, never shell snippets. Root service files, config and binary have fixed paths. Symlink/writable ancestors and non-root ownership are rejected for privileged resources. An explicit sudo invocation authorizes installing the reviewed source executable owned by root or the invoking user. Source files and ancestors must not be group/world writable or symlinked; executables belonging to other users, non-regular files and oversized or changing files are rejected. A bounded snapshot is atomically copied to the fixed root-owned service path. Service startup never runs from a user-owned source path. Identical reinstall is idempotent; `raymond setup` handles upgrades/config changes under the lifecycle lock, with previous binary/config recovery. Atomic file publication and a SHA-256 ownership journal support conservative cleanup; changed files stop uninstall rather than risk deleting unrelated state. Empty directories/logs can remain.

Linux uses a dynamic service user with CAP_NET_BIND_SERVICE; systemd-networkd separately manages its dedicated DNS link. macOS's launchd daemon runs as root for privileged ports and alias restoration. Privilege separation on macOS is a future hardening task. No remote-control API exists. Long-lived streaming requests intentionally have no short total timeout; request headers, dialing and backend response-header waits are bounded.

The remote installer downloads an immutable release tag, verifies SHA-256, rejects non-regular/path-bearing archive members and installs the binary as the invoking user. By default it then invokes native setup, which announces the DNS/service changes and requests administrator access. `RAYMOND_BINARY_ONLY=1` skips setup and profile edits. Enrolled `raymond upgrade` verifies native archives/checksums from the fixed repository and uses a durable root worker; it never executes downloaded shell code. Initial binary acquisition can still use the separately reviewed shell installer. Serving remains offline. HTTPS and a checksum from the same release do not provide independent provenance; artifact signing/attestation is a recommended release prerequisite for public distribution.

Repository maintainers must configure branch protection, required checks, private vulnerability reporting, Dependabot alerts, secret scanning and environment approval rules (`platform-validation`, `release`). These settings are not provisioned by files alone. Privileged CI only runs on disposable runners, with human environment approval configured in GitHub. Do not run it on persistent workstations or unreviewed forks.

CodeQL is conditional on repository support, as specified in the implementation plan. Public repositories run it automatically. For private repositories, first enable the available code-scanning feature in Settings → Code security, then create the repository Actions variable `RAYMOND_CODEQL_ENABLED` with value `true`. Without opt-in, its job is skipped and the Security summary reports that lack of coverage; the vulnerability scan still runs on every PR. Opting in does not suppress analysis or upload failures. The CodeQL job has contents/actions read permissions plus security-events write for its results; other checks retain read-only repository permissions.

The optional macOS `proxy.allow_wildcard_coexistence` setting relaxes only the conservative HTTP wildcard preflight rejection. It does not authorize public or localhost proxy binds, bypass exact-address availability checks, relax DNS ownership checks, change Docker settings, or alter the root-owned service paths. Existing configurations keep the strict default.

HTTP access logging records method, host, escaped URL path, final status, byte count and duration. Query strings, authorization headers, cookies and bodies are excluded. Logs are local service output; `raymond logs` uses only the fixed macOS file or the Raymond systemd unit, without a remote logging endpoint or arbitrary file selection.

## Local management work for 0.1.2

This feature branch now wires the root manager, enrollment, detached workers, dropped-UID helpers and CLI/dashboard API. Native acceptance is required before release. Its authorized boundary is a private Unix socket with separate owner/proxy credentials, single-use browser launches, persistent sessions and CSRF/Host/Origin checks. Browser management must remain on the existing dashboard listener. API inputs may select fixed actions and validated configuration or stable version numbers; they must never select shell commands, filesystem paths, executables or download URLs. Explicit update requests may use the fixed release source; normal serving must remain offline.

The operation journal stores requests privately and excludes them from API operation responses. Only one queued/running action may exist. A worker retains the journal lock throughout its lifetime, including rollback and child cleanup. Every state transition is saved atomically before the caller continues. If saving fails, further writes are blocked and the lock remains held. Startup preserves an interrupted running record and rejects automatic replay: the manager must reconcile actual service/binary state with its rollback evidence before completing the record and accepting new work. History is bounded by count and serialized size. The independent manager and restricted proxy share one protected executable. Linux owner requests use Unix peer credentials in addition to the owner token; the distinct proxy credential is delivered with systemd LoadCredential. Inherited worker descriptors are restored to close-on-exec before any helper/native subprocess. Log readers inherit daemon cancellation and return only projected request fields. Native acceptance includes real migration, replacement, owner-CLI rollback and orphan recovery on disposable runners.


Browser authentication uses no cookies on the HTTP-only dashboard. A single-use launch exchanges for a random session capability and CSRF token; the capability stays in the tab's `sessionStorage` and is sent explicitly in `X-Raymond-Session`. Reloads and service/manager updates preserve that tab's access, following the browser's tab-session storage lifecycle. A separately opened tab uses `raymond dashboard` to authorize. The manager accepts exactly one session header and never authenticates with legacy cookies. Both API calls and log streams omit cookies and reject redirects. Application routes retain precedence but strip Raymond's reserved session/CSRF headers before forwarding, including when an application shadows the dashboard hostname. The capability is accessible to same-origin JavaScript, so the strict CSP, absence of third-party scripts, and text-only config/log rendering remain essential. Server-side session tokens remain hashed at rest and expire after 30 days. Migrating from the earlier cookie format revokes those legacy sessions and pending launches; CLI upgrades automatically open a newly authorized dashboard. The optional `raymond dashboard` shortcut can reopen it later.

Dropped-UID helpers reject UID/GID values outside the native 32-bit identity range before converting them, including the all-ones sentinel that native credential syscalls interpret as leaving identity unchanged.
